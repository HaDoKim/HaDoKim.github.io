납품한 장비의 온도 컨트롤러가 어느 날 오후 잠깐 응답을 안 했습니다. 로그를 열었더니
예외가 딱 한 줄 있었습니다. 첫 실패만 남기게 해 뒀으니 당연했습니다. 그런데 정작 알고
싶은 건 **얼마나 오래 끊겼는가**였고, 그 답은 로그에 없었습니다. 결국 온도 CSV를 열어
값이 굳어 있던 행을 손으로 셌습니다.

이 글은 그 뒤에 만든 `FaultEpisode`라는 111줄짜리 클래스 이야기입니다.

## 두 가지 나쁜 선택

장비 소프트웨어의 통신 루프는 짧습니다. 이 장비는 DIO를 100ms마다, 온도를 200ms마다
읽습니다. 케이블이 빠지면 초당 열 번씩 같은 예외가 납니다.

**실패마다 남기면** 몇 분 만에 로그가 같은 줄로 뒤덮입니다. 그 사이에 섞인 다른 문제는
묻힙니다. 그래서 처음엔 **첫 건만 남기게** 했는데, 그러면 이번처럼 "언제 끝났는지"가
사라집니다. 둘 다 나중에 읽는 사람에게 필요한 걸 주지 못합니다.

## 세 순간

실패의 연속을 **에피소드**로 보기로 했습니다. 시작이 있고, 끝이 있고, 그 사이는 하나의
사건입니다. 로그에 남길 건 세 순간뿐입니다.

1. **시작** — 예외 전문. 스택까지. 원인을 찾을 때 필요한 건 첫 예외의 전체 모습입니다.
2. **예외 종류가 바뀌는 순간** — 컨트롤러가 요청을 거절하다가 아예 타임아웃으로 번지는
   경우처럼, 실패의 성격이 달라지는 건 원인 판단에 중요합니다. 같은 종류가 반복되는 건
   중요하지 않습니다.
3. **복구** — 몇 초 동안, 종류별로 몇 번 실패했는지 한 줄.

세 번째가 이번 사건에서 없었던 줄입니다.

```csharp
public sealed class FaultEpisode
{
    private readonly Dictionary<string, int> _counts = new();
    private DateTime _startedAt;
    private bool _active;

    /// 실패 한 번을 알린다. 로그에 남겼으면 true.
    public bool Fail(Exception ex)
    {
        string name = ex.GetType().Name;
        bool shouldLog;

        if (!_active)
        {
            _active = true;
            _startedAt = DateTime.Now;
            _counts.Clear();
            shouldLog = true;                     // ① 시작
        }
        else
        {
            shouldLog = !_counts.ContainsKey(name); // ② 처음 보는 종류
        }

        _counts.TryGetValue(name, out int n);
        _counts[name] = n + 1;

        if (shouldLog) ErrorLogger.Write(ex);
        return shouldLog;
    }

    /// 성공 한 번을 알린다. 이어지던 실패가 끝났으면 복구 문구를 남긴다.
    public string? Succeed()
    {
        if (!_active) return null;

        _active = false;
        double seconds = (DateTime.Now - _startedAt).TotalSeconds;
        string detail = string.Join(", ", _counts
            .OrderByDescending(p => p.Value)
            .Select(p => $"{p.Key} {p.Value}회"));

        var message = $"{_what} 복구 — {seconds:F1}초 동안 " +
                      $"{_counts.Values.Sum()}회 실패 ({detail})";   // ③ 복구
        _counts.Clear();
        ErrorLogger.WriteInfo(message);
        return message;
    }
}
```

(실제 코드는 `lock`으로 감싸 있습니다. 여기선 뺐습니다.)

복구 문구는 이렇게 나옵니다.

```
온도 읽기 복구 — 47.3초 동안 231회 실패 (TimeoutException 229회, IOException 2회)
```

이 한 줄이면 CSV를 열 필요가 없습니다.

## 복구가 아닌 것을 복구라고 쓰지 않기

만들다 보니 미묘한 지점이 두 군데 있었습니다.

**설정을 다시 읽으면 연결을 새로 만듭니다.** 이때 진행 중이던 에피소드는 어떻게 할까요.
새 연결이 성공했다고 `Succeed()`를 부르면 "복구"로 기록되는데, 그건 거짓말입니다. 끊겼던
그 연결이 돌아온 게 아니라 다른 연결을 만든 것이니까요. 그래서 `Reset()`을 따로 뒀습니다.
진행 중이던 기록을 **조용히 버립니다**. 복구 문구를 남기지 않습니다.

**시작 버튼은 통신을 고치지 않습니다.** 원래 코드에는 가동을 시작할 때 실패 플래그를
다시 무장하는 부분이 있었습니다. 작업자가 시작을 다시 누르면 다음 실패가 새 에피소드의
첫 건으로 기록됐습니다. 그런데 통신이 끊긴 상태에서 시작을 눌렀다고 통신이 복구되지는
않습니다. 그 코드를 지웠습니다. 에피소드는 **실제 성공이 있어야** 끝납니다.

둘 다 "로그가 사실을 말하는가"의 문제였습니다. 로그를 읽는 사람은 현장에 없던 사람이고,
그 사람이 로그를 믿을 수 있어야 합니다.

## 갈래를 나누기

에피소드를 하나로 두지 않고 다섯으로 나눴습니다 — 온도 컨트롤러 연결, 온도 읽기, DIO
연결, DIO 입출력 읽기, 실린더 DIO 제어. 코드가 늘어나는 게 아니라 `FaultEpisode`
인스턴스가 다섯 개 생기는 것뿐입니다.

나눈 이유는 현장에서 **볼 곳이 다르기** 때문입니다. 온도 컨트롤러 연결 실패면 시리얼
케이블과 COM 포트를 보고, DIO 입출력 실패면 이더넷 케이블과 모듈 전원을 봅니다. 하나로
뭉쳐 "통신 실패 231회"라고 나오면 어디부터 볼지 다시 로그를 뒤져야 합니다.

## 확인한 방법

테스트 이름을 그대로 옮기면 명세가 됩니다.

- 같은 예외가 이어지면 첫 건만 남긴다
- 예외 종류가 바뀌면 그것도 남긴다
- 복구하면 지속 시간과 종류별 횟수를 알려 준다
- 복구한 뒤 다시 실패하면 새 에피소드다
- 조용히 버리면 복구로 기록되지 않는다

그리고 실제 앱으로 확인했습니다. 없는 COM 포트를 지정하고 30초, 잘못된 DIO 주소를
지정하고 30초 — 각각 열다섯 번쯤 실패하는 동안 로그는 **한 줄씩만** 늘었습니다.

## 남는 생각

로그는 쓰는 사람이 아니라 나중에 읽는 사람을 위한 것입니다. 그 사람은 보통 현장에 없었고,
급하고, 로그 말고는 볼 게 없습니다. "무슨 일이 있었나"보다 "언제 시작해서 언제 끝났고
그 사이에 성격이 바뀌었나"가 그 사람에게 필요한 형태였습니다.

111줄이었고, 하루 걸렸습니다. CSV를 손으로 세던 오후보다 짧습니다.
