# 개인 홈페이지 설계

- 작성일: 2026-08-07
- 상태: 사용자 리뷰 대기
- 대상 저장소: `HaDoKim/HaDoKim.github.io`
- 공개 주소: https://hadokim.github.io

## 1. 목적

포트폴리오와 블로그를 겸하는 개인 홈페이지를 만든다. 방문자는 두 부류다.

- **채용 담당자·협업 상대** — 이 사람이 무엇을 만들 수 있는지 3분 안에 파악하려는 사람
- **검색으로 유입된 독자** — 특정 기술 문제를 검색하다 글 하나에 도착한 사람

전자를 위해 홈과 프로젝트 페이지가 존재하고, 후자를 위해 블로그가 존재한다. 후자가 전자로 전환되는 경로(글 → 소개 → 프로젝트)가 항상 열려 있어야 한다.

## 2. 확정 사항

| 항목 | 결정 |
|---|---|
| 성격 | 포트폴리오 + 블로그 |
| 글 작성 방식 | 저장소 안의 마크다운 파일 |
| 프레임워크 | Astro 7.x (Node 22.12 이상 요구) |
| 호스팅 | GitHub Pages (GitHub Actions 빌드) |
| 언어 | 한국어만. 영어는 추후 확장 |
| 디자인 톤 | 미니멀, 글 중심 |

### 프레임워크 선정 근거

Jekyll과 Next.js를 함께 검토했다.

- **Jekyll** — GitHub Pages가 공식 지원해 배포 설정이 필요 없다는 게 유일한 장점이나, 다국어 확장 시 플러그인이 필요하고 GitHub Pages 기본 빌드는 플러그인을 제한한다. 결국 Actions를 쓰게 되므로 그 장점이 사라진다.
- **Next.js** — 자료는 가장 많지만 GitHub Pages 배포에 static export와 basePath 설정이 필요하고, 이 사이트에 불필요한 개념(서버 컴포넌트, 하이드레이션)을 학습 비용으로 요구한다.
- **Astro** — 마크다운 컬렉션과 i18n 라우팅이 내장이고, 산출물이 순수 정적 HTML이라 JS 프레임워크 학습 없이 운영 가능하다. 요구사항 네 가지(마크다운·다국어 확장·정적 배포·낮은 학습 비용)를 모두 정면으로 충족하는 유일한 선택지다.

## 3. 사이트 구조

### URL

한국어를 기본 언어로 두고 **접두사를 붙이지 않는다.**

```
/                  홈
/about             소개
/projects          프로젝트 목록
/projects/[slug]   프로젝트 상세
/blog              글 목록
/blog/[slug]       글 상세
/blog/tags/[tag]   태그별 글 목록
/404               없는 페이지
/rss.xml           RSS 피드
/sitemap-index.xml 사이트맵
```

영어를 추가할 때는 `/en/` 접두사가 붙은 경로가 **추가**될 뿐, 위 주소는 하나도 바뀌지 않는다. 지금 `/ko/`로 시작하면 나중에 기존 링크와 검색 유입이 전부 깨지므로 그렇게 하지 않는다.

### 저장소 이름

저장소 이름은 사용자명과 동일하게 `HaDoKim.github.io`로 만든다. 이렇게 하면 사이트가 도메인 루트(`/`)에 놓여 `base` 경로 설정이 필요 없다. 다른 이름을 쓰면 사이트가 `/저장소이름/` 하위에 놓여 모든 자산 경로에 base를 반영해야 하고, 로컬에서는 정상이나 배포 후 CSS·이미지가 깨지는 문제가 발생한다.

접속 주소는 GitHub이 소문자로 정규화하므로 **https://hadokim.github.io** 이다.

### 페이지별 내용

| 페이지 | 구성 |
|---|---|
| 홈 | 한 줄 소개 · 대표 프로젝트 3개 · 최근 글 3개 · 연락처 링크 |
| 소개 | 자기소개, 다루는 기술, 경력 |
| 프로젝트 목록 | 카드 그리드. `featured` 항목이 상단, 그 아래 나머지가 `date` 최신순 |
| 프로젝트 상세 | 설명 본문, 사용 기술, 저장소·데모 링크 |
| 블로그 목록 | 최신순. 사이드에 태그 목록 |
| 글 상세 | 본문, 발행일, 태그, 이전/다음 글 |
| 404 | 홈과 블로그 목록으로 안내 |

### 헤더·푸터

- 헤더: 사이트 이름(홈 링크) · 소개 · 프로젝트 · 블로그 · 언어 전환 버튼
- 푸터: 저작권 표기, GitHub·이메일 링크, RSS 링크

**언어 전환 버튼은 활성 언어가 2개 이상일 때만 렌더링된다.** 지금은 한국어뿐이므로 화면에 나타나지 않는다. `en`을 추가하는 순간 자동으로 나타난다.

번역이 추가된 뒤의 전환 동작은 이렇다. 현재 페이지에 대응 번역이 있으면 그 페이지로, 없으면 해당 언어의 같은 섹션 목록으로 보낸다. 예를 들어 한국어로만 쓴 글을 보다가 EN을 누르면 `/en/blog`로 이동한다.

## 4. 콘텐츠 모델

마크다운 파일 하나가 항목 하나다.

```
src/content/
├── blog/
│   └── ko/
│       └── 2026-08-07-hello.md
└── projects/
    └── ko/
        └── dtow.md
```

지금은 `ko/`뿐이지만 나중에 `en/` 폴더를 나란히 만들어 파일을 넣으면 영어 콘텐츠가 된다. **기존 파일을 옮길 필요가 없다.**

### 파일명 규칙

- 블로그: `YYYY-MM-DD-slug.md`. 파일 탐색기에서 시간순 정렬되도록 날짜를 앞에 둔다.
- 프로젝트: `slug.md`. 날짜 접두사 없음.
- slug는 소문자 영문·숫자·하이픈만 쓴다. URL에 그대로 노출되므로 한글을 쓰지 않는다.
- **번역본은 파일명이 동일해야 한다.** `blog/ko/2026-08-07-hello.md`와 `blog/en/2026-08-07-hello.md`가 서로의 번역으로 연결된다.

**URL의 slug는 파일명에서 날짜 접두사를 제거한 값이다.** `2026-08-07-hello.md` → `/blog/hello`. 주소에 날짜가 들어가지 않으므로, 나중에 발행일을 고쳐도 링크가 깨지지 않는다.

파일명의 날짜와 frontmatter `date`는 역할이 다르다. **파일명 날짜는 파일 목록을 보기 좋게 정렬하기 위한 것일 뿐이고, 사이트의 정렬·표시에 쓰이는 값은 언제나 frontmatter `date`다.** 둘이 어긋나도 빌드는 실패하지 않는다.

### frontmatter — 블로그

```markdown
---
title: "첫 글입니다"
description: "목록과 공유 미리보기에 쓰이는 한 줄 요약"
date: 2026-08-07
tags: ["회고", "웹"]
draft: false
cover: "/images/blog/hello.png"   # 선택
---

본문은 마크다운 그대로 쓴다.
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `title` | O | 글 제목 |
| `description` | O | 목록·검색결과·SNS 공유 미리보기에 쓰임 |
| `date` | O | 발행일. 정렬 기준 |
| `tags` | X | 기본값 빈 배열 |
| `draft` | X | 기본값 `false`. `true`면 빌드에서 제외 |
| `cover` | X | 대표 이미지 경로 |

### frontmatter — 프로젝트

```markdown
---
title: "DWG Converter"
description: "CAD 도면을 일괄 변환하는 도구"
date: 2026-03-01
stack: ["C#", "WPF"]
repo: "https://github.com/HaDoKim/dwg-converter"   # 선택
demo: "https://..."                                       # 선택
featured: true
draft: false
cover: "/images/projects/dwg.png"   # 선택
---
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `title` `description` | O | 블로그와 동일 |
| `date` | O | 프로젝트 완료일. 진행 중이면 최종 갱신일. 목록 정렬 기준 |
| `stack` | O | 사용 기술 배열 |
| `repo` `demo` | X | 링크. 없으면 버튼이 표시되지 않음 |
| `featured` | X | 기본값 `false`. `true`면 홈에 노출 |
| `draft` `cover` | X | 블로그와 동일 |

### 콘텐츠 규칙

1. **`draft: true`는 빌드에서 제외된다.** 쓰다 만 글을 저장소에 그대로 커밋해도 사이트에는 나오지 않는다.
2. **번역은 의무가 아니다.** `ko/`에만 있는 글은 한국어 사이트에만 나온다. 영어 목록에는 존재 자체가 뜨지 않으므로 빈 페이지가 생기지 않는다.
3. **frontmatter는 `src/content.config.ts`의 스키마로 검사된다.** 필수 필드 누락이나 타입 오류는 빌드를 실패시키며, 오류 메시지에 파일 경로가 포함된다.
4. **이미지는 `public/images/` 아래에 둔다.** 블로그는 `public/images/blog/`, 프로젝트는 `public/images/projects/`.
5. **홈에 노출되는 개수는 각각 3개로 고정한다.** `featured: true`인 프로젝트가 3개를 넘으면 `date` 최신순 상위 3개만 나온다. 최근 글도 같은 방식이다. 항목이 늘어나 홈이 길어지는 일이 없다.

## 5. 영어 확장 대비

지금 영어를 만들지는 않지만, 나중에 추가할 때 구조를 뜯어고치지 않도록 세 가지를 미리 잡는다.

1. **URL에 기본 언어 접두사를 쓰지 않는다.** (3절) 영어 추가 시 기존 한글 주소가 그대로 유지된다.
2. **콘텐츠 폴더를 언어별로 나눈다.** (4절) 파일 이동 없이 `en/` 폴더 추가만으로 확장된다.
3. **화면 문구를 코드에서 분리한다.** 아래 참조.

### 화면 문구 분리

"최근 글", "프로젝트 더 보기", "작성일" 같은 UI 텍스트를 컴포넌트에 직접 쓰지 않고 `src/i18n/ui.ts` 한 곳에 모은다.

```typescript
export const defaultLang = 'ko';
export const languages = { ko: '한국어' };   // en 추가 지점

export const ui = {
  ko: {
    'nav.about': '소개',
    'nav.projects': '프로젝트',
    'nav.blog': '블로그',
    'home.recent': '최근 글',
    'home.featured': '주요 프로젝트',
    'post.date': '작성일',
    // ...
  },
} as const;
```

영어 추가 작업이 "코드 전체를 뒤져 한글 문자열을 찾아내는 일"이 아니라 "파일 하나를 번역하는 일"이 된다. `languages`에 `en`이 등록되는 순간 언어 전환 버튼도 자동으로 나타난다.

**`src/pages/`의 폴더 구조가 곧 사이트 주소다.** `pages/about.astro`는 `/about`이 된다. 페이지를 추가하려면 이 폴더에 파일을 만들면 되고, 라우팅 설정 파일은 없다.

### 컴포넌트 경계

각 조각이 하나의 역할만 갖도록 나눈다.

- **레이아웃** — 페이지 뼈대와 `<head>` 메타태그를 책임진다. 콘텐츠를 모른다.
- **컴포넌트** — 넘겨받은 데이터를 그리기만 한다. 파일 시스템을 직접 읽지 않는다.
- **페이지** — 콘텐츠를 조회·정렬·필터링해 컴포넌트에 넘긴다.

`PostCard`는 글 하나를 받아 카드를 그리는 것 외에 아무것도 하지 않으므로, 홈·블로그 목록·태그 페이지에서 그대로 재사용된다.

## 7. 빌드와 배포

### 로컬 작업 흐름

```bash
npm run dev
```

로컬 서버가 뜨고, 파일을 저장하면 브라우저에 즉시 반영된다. 글을 쓰면서 결과를 바로 확인할 수 있다.

### 배포

`main` 브랜치에 push하면 GitHub Actions가 빌드해 Pages에 올린다. 반영까지 2~3분.

```
git push  →  Actions: npm ci → npm run build  →  Pages 배포
                              ↓ 실패 시
                          배포 중단 (기존 사이트 유지)
```

### 검증

개인 홈페이지에 유닛 테스트는 과하다. 대신 **빌드 자체가 검사기 역할을 한다.**

| 검사 대상 | 검출 방식 |
|---|---|
| frontmatter 필수 필드 누락·타입 오류 | 컬렉션 스키마 검증 → 빌드 실패 |
| 존재하지 않는 이미지 참조 | 빌드 실패 |
| 깨진 내부 링크 | `astro check` |
| 타입 오류 | `astro check` |

빌드가 실패하면 배포되지 않으므로 **망가진 사이트가 공개되는 경로가 구조적으로 막혀 있다.** 배포 워크플로는 `astro check`와 `astro build`를 순서대로 실행하고, 하나라도 실패하면 중단한다.

### 런타임 에러 처리

정적 사이트라 서버 오류가 없다. 방문자가 마주칠 수 있는 상황은 하나뿐이다.

- **없는 주소** — 404 페이지가 받아 홈과 블로그 목록으로 안내한다.

## 8. 디자인

미니멀, 글 중심. 여백을 넓게 쓰고 장식을 최소화한다. 이미지가 없어도 허전해 보이지 않는 구성으로 만든다.

| 항목 | 결정 |
|---|---|
| 본문 폰트 | Pretendard (한글), 시스템 폰트 폴백 |
| 코드 폰트 | 시스템 모노스페이스 |
| 본문 너비 | 약 65~75자 |
| 색 | 무채색 바탕 + 포인트 색 1개 (링크·강조) |
| 다크 모드 | 지원. 시스템 설정을 따르되 수동 전환 가능 |
| 반응형 | 모바일 우선. 한 단 → 데스크톱에서 카드 그리드 |

**한글 웹폰트는 용량이 크므로 서브셋으로 나눠 필요한 글자만 내려받게 한다.** 통짜로 넣으면 첫 화면 로딩이 눈에 띄게 느려진다.

다크 모드 선택은 `localStorage`에 저장하고, 화면이 그려지기 전에 적용해 새로고침 시 흰 화면이 번쩍이지 않게 한다.

접근성은 기본선을 지킨다. 본문 대비비 4.5:1 이상, 이미지 `alt` 필수, 키보드 포커스 표시 유지, 헤딩 단계 건너뛰지 않기.

## 9. 포함하되 최소로

- **RSS 피드** (`/rss.xml`) — 블로그의 표준 기능이고 설정이 몇 줄이다.
- **사이트맵** — 검색 노출은 포트폴리오 목적에 직결된다.
- **Open Graph 태그** — 링크를 공유했을 때 제목·요약·이미지가 뜨게 한다.
